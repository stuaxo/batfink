    What the machine is doing

    There is no firmware here. The program pages both ROMs out and writes straight to the hardware, which is how demos were actually written.

    &7F00
    Gate Array. Picks an ink, sets its colour, and selects the screen mode.
    &F500
    PPI port B. Bit 0 goes high during the vertical sync pulse, which is how the program stays at 50Hz.
    &0038
    Interrupt vector. The CPC interrupts six times a frame, every 52 scanlines.
    &C000
    Screen memory. 16K, and famously not linear: eight interleaved blocks of &800, one per raster line within a character row.

    The colour bands are ink 0 being rewritten twelve times while the CRT is still drawing the picture, three scanlines apart, from inside the interrupt handler. That effect costs exactly what it covers: 36 scanlines of screen means 36 scanlines of processor time gone. The rest of the frame has to fit in what is left, which is why the sprites are cheap and the scrolling text runs in a window rather than the full 320 pixels. As written it uses about 280 of the 312 scanlines in a frame.

    Instructions are charged the way the Gate Array charges them: every one is stretched to a multiple of four T-states, and the interrupt counter is resynchronised two scanlines into the vertical sync pulse. Without both of those, hand-timed raster code lands in the wrong place.

    Checking it on another emulator

    Download .sna writes a version 2 CPC snapshot: a 256-byte header holding the Z80 registers, the Gate Array palette and mode, the CRTC registers and the PPI state, followed by all 64K of RAM. It is captured at the entry point with both ROMs already paged out, so nothing depends on firmware being present. Drop the file on any of these and it should look the same:

    tiny8bit
    Andre Weissflog's WebAssembly CPC at floooh.github.io/tiny8bit/cpc.html. The cpc-ui build adds a Z80 disassembler and memory viewer, which makes it the most useful of the three for finding out why something differs.
    CPCBox
    A JavaScript CPC at cpcbox.com, cycle-accurate enough for demo code.
    WinAPE / Caprice32 / RVM
    Desktop emulators. WinAPE in particular has a good debugger and is the usual reference for CPC timing.

    Two things will not match. There is no sound here at all, so any PSG registers in the snapshot are zero. And while instruction timing follows the Gate Array's four-cycle rule, it is charged per instruction rather than per machine cycle, so a raster split placed to the exact T-state may drift by a few cycles against a reference emulator.

    The assembler supports labels, org, equ, db, dw, ds, the full base instruction set, CB shifts and bit operations, ED block moves, and the IX / IY index registers. Numbers can be written &FF, #FF, 0xFF, %1010 or plain decimal. Execution starts at the label start.
